the viewer watches the code actually change on screen (buggy -> the fix
-> corrected), narrated step by step, not one static code block shown

Requirements:
- Pick ONE specific, narrow topic (a real gotcha, a surprising behavior, a
  "why does this happen" moment) — not a broad topic like "JavaScript
  tips".
- The narration MUST include one genuine hook, opinion, or gotcha that is
  not just restating a fact. This is non-negotiable — YouTube's
  inauthentic-content policy penalizes videos that look interchangeable or
  template-generated with no real point of view.
- The FIRST line of narration must lead with the PAYOFF — the actual,
  concrete consequence of the bug/gotcha, stated directly — not
  "Picture this..." or "Here's a story about..." (scene-setting) and
  not a generic tease like "this will break in production" that could
  describe almost any bug. The viewer decides whether to keep watching
  in the first couple seconds; a story-opening wind-up and a vague tease
  waste that window the same way. Lead with the specific, real
  consequence — what keeps the viewer watching past it is wanting to
  see WHY it happens, which the rest of the steps then show.
    - BAD (flat description of the code, no payoff): "This function
      uses a mutable default argument."
    - BAD (generic tease, no concrete consequence): "This is a bug that
      will get you in trouble later."
    - GOOD (payoff-first — the actual, specific consequence): "This
      function remembers every call you've ever made to it — and
      that's not a feature."
- Break the demo into 2-4 STEPS. Each step is one beat of the story, and
  each has its own CODE (what's on screen during that step) and its own
  SCRIPT (the narration spoken during that step, timed to match). A
  typical shape:
    Step 1: the buggy/surprising code, and what it actually
      produces (OUTPUT) — the wrong or confusing result.
    Step 2 (and 3, if needed): the code changing — show the actual edit,
      explain why.
    Last step: the corrected code, and its OUTPUT — the right result.
  Use 2 steps (buggy -> fixed) whenever possible, 3 only if the fix
  genuinely needs a middle step. Never 4 -- it can't fit the length
  limit below.
- Each step's CODE is the FULL code as it should appear on screen at that
  point (not a diff) — repeat unchanged lines from the previous step.
- OUTPUT is what that step's code actually prints/returns/does — written
  exactly as it would appear in a real terminal. If multiple lines get
  printed, put each on its own real line (an actual line break in your
  output), never a literal backslash-n — a terminal never shows the two
  characters "\n", it shows a new line.
  - BAD: [[1, 2, 99], [3, 4]]\n[[1, 2, 99], [3, 4]]
  - GOOD:
    [[1, 2, 99], [3, 4]]
    [[1, 2, 99], [3, 4]]
  Skip OUTPUT (write "(none)") for a step that's pure narration with no
  new result (e.g. a step that's just explaining WHY, with the same code
  as before).
- Each step's SCRIPT is spoken narration ONLY — plain prose, describing
  the code in words a person would actually say out loud. NEVER put
  literal code syntax, symbols, or punctuation-heavy fragments in SCRIPT
  (no `=`, `[]`, `()`, `def foo():`, etc.) — a TTS engine will try to
  pronounce them literally and mangle the narration.
  - BAD (breaks TTS): "Write def add_item(item, cart=[]) and every call
    shares the same list."
  - GOOD (describes it in words): "Define a function with an empty list
    as its default argument, and every call that skips that argument
    shares that exact same list."
- Total SCRIPT length across ALL steps combined: 60-75 words -- a HARD
  limit, spoken in about 25-30 seconds (edge_tts paces ~2.6 words/sec).
  Why so short (2026-09-25): real channel data -- viewers left at ~20s
  no matter how long the video was (45-50s videos averaged 35-47%
  watched), and YouTube stops pushing a Short past its ~1,000-view test
  audience when most viewers leave early. A 22s video watched for 20s
  is nearly complete, and replays count.
  Split that budget across steps roughly by how much each step has to
  say — a short "here's the fix" step doesn't need the same word count as the setup step. Conversational pace, no
  filler, no "hey guys" or "let's dive in" openers.
